## Build e CI

O repositório possui os workflows:

```text
.github/workflows/architecture-boundary.yml
.github/workflows/build-apk.yml
```

O workflow `Architecture boundary` executa em pull requests para `master` e em pushes para `master`.

Ele também exige que branches de pull request expressem uma classe SemVer:

- `feature/*` -> minor;
- `fix/*`, `bugfix/*`, `hotfix/*` -> patch;
- `major/*`, `breaking/*` -> major.

A branch inicialmente criada para documentar o plano (`docs/architecture-hardening-plan`) não atendia essa regra e foi substituída pela branch compatível:

```text
feature/architecture-hardening-plan
```

O PR original foi encerrado sem merge e substituído pelo PR #19.

Na execução do PR #19 para o commit que continha o plano e o primeiro registro deste baseline, o workflow `Architecture boundary` concluiu com sucesso. O job `Verify Tuya boundary` passou, assim como a classificação SemVer da nova branch.

No commit de referência do `master`, a consulta de status não retornou status checks publicados nem workflow run associado ao SHA. Isso não deve ser interpretado como falha do código; significa apenas que não há evidência de CI anexada especificamente a esse SHA disponível pela consulta realizada durante esta fase.

O workflow `Build APK` não roda automaticamente em pull requests; ele está configurado para `workflow_dispatch` e push em `master`. Portanto, a Fase 0 não atribui falsamente ao PR uma validação de build APK que o workflow atual não executa.

## Verificação física

As verificações abaixo dependem de um aparelho Android e do T4A físico e não podem ser executadas pelo agente GitHub. Elas permanecem como checklist obrigatório de campo antes de considerar o baseline funcional revalidado em hardware:

- [ ] instalação in-place sobre o APK existente;
- [ ] restauração de sessão;
- [ ] conexão BLE;
- [ ] reconexão BLE;
- [ ] leitura de velocidade;
- [ ] leitura de bateria;
- [ ] farol;
- [ ] partida;
- [ ] cruzeiro;
- [ ] todos os modos de condução;
- [ ] bloqueio;
- [ ] desbloqueio;
- [ ] bloqueio automático;
- [ ] publicação MQTT;
- [ ] geolocalização.

Nenhum item desta lista deve ser marcado como validado sem execução real no dispositivo.

## Log raw de referência

O baseline de campo deve preservar ao menos um log raw representativo contendo no início a identificação da versão emitida pela sessão:

```text
VERSION {"versionName":"...","versionCode":...}
```

O log deve cobrir, sempre que possível, conexão, RX de velocidade e bateria e pelo menos um comando com confirmação por RX.

Não será criado um log sintético para satisfazer este item: somente um log obtido em execução real é válido como evidência de baseline.

## Critério para comparação futura

Durante as fases seguintes, uma alteração será considerada regressiva se, comparada ao commit de referência acima, modificar involuntariamente qualquer um dos comportamentos congelados neste documento.

A comparação deverá usar três fontes de evidência:

1. testes automatizados, conforme forem introduzidos na Fase 1;
2. build e checks do GitHub;
3. validação física e log raw quando a alteração afetar comportamento observável no T4A.
